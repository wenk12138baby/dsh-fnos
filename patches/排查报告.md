## 2. dsh 0.2.x 的两道「坑」（白屏的真正来源）

### 坑 A：进程 token + Host 绑定签名 cookie

`@deepseek-ai/dsh-client-connection` 的 `BrowserAuth`：

- 启动时打印 `dsh web: http://127.0.0.1:3080/?token=XXXX`
- `authorizeIndex()`：根路径必须带 token，验证通过后返回 **303 + Set-Cookie**
- Cookie 的签名 payload 里带 `authority`，由请求的 **Host 头** 派生：

```js
function requestAudience(headers, secure) {
  const host = header(headers, "host");
  const url = new URL(`${secure ? "https:" : "http:"}//${host}`);
  return secure ? url.origin : url.host;   // ← 例如 "192.168.1.10:3080"
}
```

- `isAuthenticated()` 读取 cookie 时**再次**用当前请求的 Host 重算 authority，
  不一致就判无效 → 走 `writeUnauthorized()` → `401 dsh web authentication required`。

**结论**：cookie 与 Host 强绑定。用 `Host=127.0.0.1:3080` 换来的 cookie，
拿去配 `Host=192.168.1.10:3080` 的请求，签名必然不匹配。

### 坑 B：/api 的浏览器信任围栏

```js
function isTrustedApiRequest(request, trustedHosts, bindHost, protocol) {
  const hostUrl = parseAuthority(host);
  if (!isLoopbackHostname(hostUrl.hostname)
      && !isTrustedAuthority(hostUrl, trustedHosts, protocol)
      && !isBindAddressAuthority(hostUrl, bindHost)) return false;
  if (header("sec-fetch-site") === "cross-site") return false;
  ...
}
```

`cmd/main` 的 `build_trusted_args()` 会把本机 LAN IPv4 全部加进 `--trusted-host`，
所以 Host 围栏这一关**本来是通过的**。真正卡死的是坑 A。

### 坑 C：dsh webserver 默认 gzip

`dsh-web-app/cordis.patch.yml`：

```yaml
- id: webserver
  config:
    compression: gzip
    compressionLevel: 1
    compressionThresholdBytes: 1024
```

只要浏览器发 `Accept-Encoding: gzip`，`index.html`（~37 KB）就会被 gzip。
代理如果直接对 gzip 字节流做 `toString("utf8")` 再字符串替换，轻则改写无效，
重则内容损坏。

## 3. 原版 proxy.js 的四个具体缺陷

| # | 位置 | 问题 | 后果 |
|---|---|---|---|
| 1 | `ensureAuthWithRetry()` + `buildHeaders()` | 无条件用 `127.0.0.1:3080` 换 cookie，再把它注入到 Host=NAS-IP 的请求里 | 签名 authority 不匹配 → `/api` **401** → 前端 RPC 全挂 → **白屏** |
| 2 | 同上 | 无条件删除 `origin` / `sec-fetch-*`，并把 Host 改写成 loopback | 掩盖了真实问题，且 cookie 依然不匹配（因为 dsh 用的是 Host 不是 Origin） |
| 3 | `rewriteBody()` 的 `REWRITE_PREFIXES` 循环 | 只匹配 `"${p}`，即 `"/assets/`。前端 bundle 里大量是相对字面量 `"./assets/index-xxx.js"`、`"./vendor-xxx.js"`，匹配不到 | `__vite__mapDeps` 等映射表保持 `./assets/...`，依赖 `<base href>` 兜底 |
| 4 | 响应处理段 | 完全不看 `content-encoding` | gzip 响应被跳过改写（或损坏）→ `<base href="./">` 保持原样 → 资源从 `/app/` 解析 → 404 → **白屏** |

第 3、4 条叠加：即使 `<base href>` 改对了，第 1 条的 401 一样让页面起不来；
反过来，即使 /api 能通，`<base href>` 错也一样白屏。**两个问题必须同时修**。

补充一处隐患：原版

```js
out = out.replace(/<base href="\.\/">/g, `<base href="${GATEWAY_PREFIX}/">`);
```

依赖 dsh 精确输出 `<base href="./">`。这个 base 由
`dsh-host-frontend-static` 在 `renderIndex()` 里拼接：

```js
ctx.webServer.renderIndex(await readFile(distIndex, "utf8"))
   .replace(/<head(?:\s[^>]*)?>/i, (open) => `${open}<base href="./">`);
```

一旦 dsh 改了这一行，代理会静默失效。修复版增加了「找不到就自己补一个」的兜底。

## 4. 验证过程（Windows 侧实测）

用 fpk 内的 dsh 源码 + 本机 Electron 的 `ELECTRON_RUN_AS_NODE` 起真实服务：

```
dsh  → http://127.0.0.1:13081  (带 --trusted-host)
代理 → http://127.0.0.1:13083  (unix socket 换成 TCP 便于测试)
模拟 Host: 192.168.1.10:13083
```

| 检查项 | 原版代理 | 修复版 |
|---|---|---|
| `/app/deepseekharness` 无 cookie | 401 | 401（预期，需先用 token 交换） |
| `?token=…` 交换 | 303，但 cookie authority=`127.0.0.1:13081` | 303，cookie authority=`192.168.1.10:13083` ✅ |
| index.html | 200，`<base href="./">` 未改 | 200，`<base href="/app/deepseekharness/">` ✅ |
| `randomUUID` polyfill | 未注入 | 已注入 ✅ |
| 入口 script | `./assets/index-CN7NIWNw.js` | `/app/deepseekharness/assets/index-CN7NIWNw.js` ✅ |
| `/api/session/list` | 401 | **200 + 正常 RPC 信封** ✅ |
| `/plugins/??…` combo bundle | — | 200，9.1 MB ✅ |

> 注：fpk 里的 `node_modules` 只带 `linux-x64` 原生模块
> （`node-addon-require-builtin`、`libreoffice-kit` 等），
> 所以 Windows 上只能用**本机安装的同版本 dsh** 做等价验证；
> 前端 dist、proxy 逻辑、认证逻辑三者与 Linux 包完全一致。

## 5. 修复版 proxy.js 的改动

文件：`fpk-fix/proxy.js`（可直接替换 `app/proxy.js`，接口与调用方式不变）

```
用法: node proxy.js <socketPath> <gatewayPrefix> <target> [logFile]
环境变量: DSH_PROXY_TRUSTED="host1,host2"   # 追加可信 authority
```

1. **mirror 了 dsh 的信任围栏**（`hostAccepted()`）：
   loopback / 本机网卡 IP / `--trusted-host` 白名单 → **原样转发**（保留 Host 与 Origin，
   cookie 由浏览器自己带），这样 token 交换出来的 cookie authority 天然正确。
2. 只有 Host 不被接受时，才回落到 loopback 身份转发 + 注入 cookie（并记日志）。
3. **必须处理 gzip**：`inflate()` → `rewriteBody()` → `deflate()`，
   支持 `gzip` / `br` / `deflate`。实测 dsh 走 `gzip`、level 1。
4. 相对路径改写修正为 `".${p}`（原版等价写法是 `"./${p}`，因为 `p` 已含前导 `/`）；
   保留 dsh 刻意设计的 document-relative `plugins/…` 引用不动。
5. `<base href>` 改动 + 兜底注入；`crypto.randomUUID` polyfill 保留。
6. `assets/` 加 `cache-control: no-cache`，避免升级后拿到旧 bundle。
7. WebSocket upgrade 同样走信任围栏分支。

## 6. 落地步骤（在 fnOS 上）

```bash
# 1) 备份原代理
cp ${TRIM_APPDEST}/proxy.js ${TRIM_PKGVAR}/proxy.js.bak
# 2) 覆盖
cp proxy.js ${TRIM_APPDEST}/proxy.js
chmod 755 ${TRIM_APPDEST}/proxy.js
chown deepseekharness:deepseekharness ${TRIM_APPDEST}/proxy.js
# 3) 重启应用（应用中心 或）
TRIM_APPDEST=/var/apps/deepseekharness/target bash ${TRIM_APPDEST}/../cmd/main stop
TRIM_APPDEST=/var/apps/deepseekharness/target bash ${TRIM_APPDEST}/../cmd/main start
# 4) 看日志
tail -f ${TRIM_PKGVAR}/dsh.log
```

重打包时直接把 `fpk-fix/proxy.js` 放进 `app.tgz` 的 `proxy.js` 位置即可，
`cmd/main`、`ui/config`、`manifest` 都不用动。

## 7. 若仍白屏，按此顺序看

1. `dsh.log` 里有没有 `dsh web: http://127.0.0.1:3080/?token=…`
   —— 没有说明 dsh 根本没起来（看 `Node.js 运行时不可用` / `程序文件缺失`）。
2. 浏览器 F12 → Network：
   - `index.html` 里 `<base href>` 是否为 `/app/deepseekharness/`
   - `/app/deepseekharness/assets/index-*.js` 是否 200
   - `/app/deepseekharness/plugins/??…` 是否 200
   - `/app/deepseekharness/api/…` 是否 200（401 就是 cookie/authority 问题）
3. Console 里 `randomUUID` / `__ModuleLoader__` / `__DSH_BOOT__` 相关报错。
4. `dsh.log` 里 `[proxy]` 开头的行（修复版新增），会记录回落认证失败原因与改写跳过原因。
